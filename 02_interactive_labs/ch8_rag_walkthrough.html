The Problem
Why LLMs Need RAG
Bare LLMs have three critical limitations for production use. RAG solves all three without retraining.
🗓️

Knowledge Cutoff

Training data ends at a fixed date. The model literally cannot know anything that happened after that — no news, no updates, no new docs.

🔒

No Private Data

Your internal docs, customer records, codebases, and proprietary knowledge were never in the training set. The model has no access to them.

👻

Hallucination

When the model doesn't know, it guesses — confidently. Without grounding in real source documents, outputs can't be verified or trusted.

The Concept
What RAG Actually Means
Three words. Each one is a distinct step in the pipeline.
R
Retrieval
Search a knowledge base for documents relevant to the user's question. Use semantic vector search — not just keyword matching.
A
Augmented
Inject the retrieved documents into the prompt as context. The model now "sees" relevant knowledge it never trained on.
G
Generation
The LLM generates its answer grounded in the retrieved context — not from memory alone. Hallucination surface area collapses.

Retrieval Methods
Dense vs Sparse Retrieval
Semantic search finds conceptually related content. Keyword search finds exact terms. Hybrid uses both.

Dense Retrieval

Semantic / Embedding

Embeds both query and documents into vector space. Finds semantic matches — synonyms, paraphrases, related concepts — even without shared keywords.

Query: "How do I shrink a model?"
Finds: "quantization reduces model size", "parameter pruning", "knowledge distillation" — even without "shrink"

Sparse Retrieval

Keyword / BM25

Matches on term frequency and inverse document frequency. Fast and interpretable. Fails on synonyms and conceptual queries, but dominates exact-term lookup.

Query: "CUDA out of memory error"
Excels: returns every doc containing the exact phrase — dense embedding may dilute this signal across semantic neighbors

Hybrid Retrieval (Best of Both)

Dense + Sparse + RRF Fusion

Reciprocal Rank Fusion (RRF) merges ranked lists from both methods. Consistently outperforms either alone in production benchmarks. Used by Elasticsearch, pgvector + pg_bm25, Weaviate, Qdrant.

final_score = α × dense_score + (1-α) × sparse_score # α ≈ 0.7 typical

Load documents and split into chunks

Choose a chunking strategy based on your document type. Overlap prevents context from being cut at chunk boundaries.
from langchain.document_loaders import PyPDFLoader, DirectoryLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter

# Load documents
loader = DirectoryLoader("./docs", glob="**/*.pdf", loader_cls=PyPDFLoader)
documents = loader.load()

# Recursive splitter — tries paragraph → sentence → word
splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,       # tokens per chunk
    chunk_overlap=64,     # overlap prevents boundary cuts
    separators=["\n\n", "\n", ". ", " ", ""],
    length_function=len,
)

chunks = splitter.split_documents(documents)
print(f"Split {len(documents)} docs into {len(chunks)} chunks")

# Each chunk preserves source metadata
# chunk.metadata = {"source": "doc.pdf", "page": 3}

Embed chunks and store in a vector database

Each chunk becomes a high-dimensional vector. pgvector stores them in Postgres with full SQL querying power alongside vector search.
from langchain.embeddings import OpenAIEmbeddings
from langchain.vectorstores import PGVector
import os

# Embedding model — 1536-dim for text-embedding-3-small
embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small",
    openai_api_key=os.environ["OPENAI_API_KEY"],
)

# pgvector connection string
CONNECTION_STRING = "postgresql+psycopg2://user:pass@localhost/ragdb"
COLLECTION_NAME = "knowledge_base"

# Create vectorstore and embed all chunks in batches
vectorstore = PGVector.from_documents(
    documents=chunks,
    embedding=embeddings,
    collection_name=COLLECTION_NAME,
    connection_string=CONNECTION_STRING,
    pre_delete_collection=False,  # True to rebuild from scratch
)

print(f"Stored {len(chunks)} vectors in pgvector")

# Incremental updates — add new docs without full rebuild
# vectorstore.add_documents(new_chunks)

Retrieve relevant chunks for a query

The retriever embeds the query and finds the nearest vectors by cosine similarity. MMR diversifies results to avoid repetition.
from langchain.retrievers import EnsembleRetriever, BM25Retriever

# Dense (semantic) retriever
dense_retriever = vectorstore.as_retriever(
    search_type="mmr",          # Maximal Marginal Relevance — diversity
    search_kwargs={
        "k": 6,               # return top-6 chunks
        "fetch_k": 20,         # fetch 20, re-rank to 6
        "lambda_mult": 0.7,    # 0=max diversity, 1=max relevance
    },
)

# Sparse (keyword) retriever
bm25_retriever = BM25Retriever.from_documents(chunks)
bm25_retriever.k = 6

# Hybrid = Dense + Sparse with Reciprocal Rank Fusion
hybrid_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, dense_retriever],
    weights=[0.3, 0.7],
)

# Retrieve
query = "How does QLoRA reduce VRAM usage?"
docs = hybrid_retriever.get_relevant_documents(query)

for i, doc in enumerate(docs):
    print(f"[{i+1}] {doc.metadata['source']} — {doc.page_content[:80]}...")

Generate a grounded answer with citations

The retrieved chunks become the context window. A structured prompt forces grounded responses and enables citation extraction.
from langchain.chat_models import ChatOpenAI
from langchain.chains import RetrievalQAWithSourcesChain
from langchain.prompts import PromptTemplate

# Grounded prompt — forces source-cited answers
PROMPT = PromptTemplate(
    template="""You are a technical assistant. Answer ONLY from the provided context.
If the context does not contain the answer, say "I don't have information on that."
Never make up information not present in the context.

Context:
{summaries}

Question: {question}
Answer (cite sources as [doc_name]):""",
    input_variables=["summaries", "question"],
)

# Chain: retriever → prompt → LLM → answer + sources
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

chain = RetrievalQAWithSourcesChain.from_chain_type(
    llm=llm,
    chain_type="stuff",       # stuff = inject all chunks at once
    retriever=hybrid_retriever,
    chain_type_kwargs={"prompt": PROMPT},
    return_source_documents=True,
)

result = chain({"question": "How does QLoRA reduce VRAM?"})
print(result["answer"])
print("\nSources:", result["sources"])
Reference
RAG Cheat Sheet

Chunk Size Rules

  • 128–256 tokens — Q&A, precise facts
  • 512 tokens — general knowledge base
  • 1024+ tokens — long-form reasoning
  • Overlap — 10–20% of chunk size
  • Semantic — best quality, slowest build

Embedding Models

  • text-embedding-3-small — fast, cheap, 1536-dim
  • text-embedding-3-large — best OpenAI, 3072-dim
  • bge-m3 — best open-source multilingual
  • e5-mistral-7b — top open-source English
  • Normalize — always L2-normalize before cosine

Vector Databases

  • pgvector — Postgres extension, SQL native
  • Qdrant — production-grade, filtering
  • Weaviate — hybrid search built-in
  • FAISS — in-memory, research/dev
  • Pinecone — managed, no infra

Retrieval Params

  • k — chunks returned (4–8 typical)
  • fetch_k — over-fetch for MMR (3–5× k)
  • lambda — MMR diversity (0.6–0.8)
  • threshold — min similarity score (0.7+)
  • reranker — cross-encoder for top-k

When RAG Fails

  • Bad chunks — split mid-sentence, lost context
  • Retrieval miss — wrong embedding model
  • Context flood — too many chunks dilute answer
  • Lost in the middle — LLM ignores center context
  • No reranking — raw k-NN isn't precision-ranked

Advanced Patterns

  • HyDE — embed hypothetical answer, not query
  • Step-back — rewrite query before retrieval
  • Multi-query — 3–5 query variations, merge
  • Self-RAG — model decides when to retrieve
  • CRAG — correct retrieved docs before use
